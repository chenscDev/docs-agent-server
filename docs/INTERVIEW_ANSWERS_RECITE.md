# 面试可背诵完整答稿（阿里云 + 蚂蚁 · 对照 docs-agent）

> **用法**  
> 1. 每题先背 **【口述稿】**（约 45～90 秒）；被追问再看 **【展开要点】**。  
> 2. **【项目锚点】** 是怕忘细节时的「证据」：对应仓库里的真实能力，勿夸大。  
> 3. **【解释】** 帮你理解「为什么这么答」，上场可不念。  
> 4. 阿里 / 蚂蚁分章；重叠题在文末有 **对照表**，两边话术可复用、侧重点不同。

**项目一句话（两边通用，先背熟）：**  
「我做了一个私有文档问答 Agent：React Native 薄客户端，FastAPI 上跑 RAG 和手写 Function Calling；文档要过 pending→ready 状态机才能检索；问答走 SSE，能看到工具轨迹和流式答案；引用对齐 chunk 主键，点开再拉全文；固定 25 题评测回归。」

**技术锚点速记：**  
`docs-agent-server`（大脑）+ `rn-biz-0.86/src/docs-agent`（UI）· SQLite 存正文 · FAISS 存向量 · 通义 Chat/Embed/Rerank/OCR · `search_docs`≤2 · 历史≤8 条/~3000 字 · 评测 `eval/results/eval_20260727_164011`（25/25）

## A1. 工业 PDF：正文和表格拆成独立 chunk 后，跨元素语义关系丢了，怎么重建？

**【口述稿】**  
我项目里用结构化切分，chunk 可以带 `heading`，docx 会把表格抽成文本；但**确实没有显式的「正文块—表格块」边**，同页关联主要靠标题层级间接保留。如果要在生产重建跨元素关系，我会三板斧：第一，切分时写入 `page_id`、`table_id`、父标题；第二，表格块把**表头复制进每一行块**，避免行块脱离列含义；第三，检索命中后做**同页或同父标题扩召回**，把兄弟块一并送给模型。跨页大表还要单独做合并。我现在演示语料偏手册条款，优先做了 heading 和 Rerank；跨元素边是明确的下一步，而不是已经做完。

**【项目锚点】** P3-D3 结构化切分 · `metadata_json.heading` · docx 表抽取 · 未做 page 边  
**【解释】** 先承认缺口，再讲可落地方案，比假装「已经关联好」安全。

## A2. Embedding 对数字不敏感，公差值这类怎么保证向量能召回？

**【口述稿】**  
纯向量对「0.02 / 0.05」这类细粒度数字确实弱。我这边没有单独建数字索引，但有两层补救：一是召回后走云 **Rerank**（gte-rerank-v2），字面和数字匹配往往比纯向量强，失败还有本地词重叠兜底；二是答案必须带可点的 `[n]` 引用，对上 chunk 原文，避免「召回飘了还编数字」。生产上更稳的是**混合检索**：BM25/关键词专搜数字和单位，或把「数字+单位」规范化写进 chunk。公差场景我会优先关键词补召 + Rerank，而不是只加 Embedding 维度。

**【项目锚点】** P3-D1 Rerank · `usage.rerankUsed` · 引用收紧 P3-D2  
**【解释】** 数字题本质是「检索模态」问题，不要只答「换更大模型」。

## A3. Top-K 里文档互相矛盾，怎么用 Prompt 引导模型？

**【口述稿】**  
我会在 System 里写清：只能依据工具返回的证据；若证据冲突，**并列给出不同说法并标注来源 chunk，禁止自行调和成一个「平均结论」**；若无法判断时效，就明确说冲突未裁决。我项目里还要求无命中必须拒答，citations 只映射本轮合法 `[n]`，避免挂假引用。冲突仲裁如果要做产品能力，应靠文档**生效日期/版本**元数据排序，而不是让模型拍板。当前评测语料是单本虚构手册，冲突少，所以策略主要在 Prompt，没有做版本引擎。

**【项目锚点】** 拒答 Prompt · citation 合法性 · 单语料评测  
**【解释】** 面试官想听「不让模型私自和解冲突」。

## A4. 用户故意回避或撒谎，Agent 能否感知？感知后策略怎么调？

**【口述稿】**  
我的场景是**制度文档问答**，不是审讯或陪伴。策略是**证据优先**：用户口述与文档不一致时，以检索到的制度为准，并引用原文；不会根据用户「我说就是」改写事实。若问题明显域外，直接拒答。真要做行为感知，需要一致性检查、关键追问、风险标记，那是另一类对话 Agent。我没有上用户意图分类模型，但产品边界是清楚的：不把聊天内容写成知识库事实。

**【项目锚点】** 拒答域外 · 只依据 tool 结果  
**【解释】** 答「感知」时先划场景，避免吹成情感/反欺诈 Agent。

## A5. MCP 工具返回特别大的 JSON，怎么截断且不丢有诊断价值的信息？

**【口述稿】**  
核心思想是**上下文里放摘要和指针，详情外置按需取**。我项目虽没接 MCP，但引用就是这套：SSE 里 citations 只带短 snippet，用户点击再请求 `GET /v1/chunks/{chunkId}` 拉全文——既省 Token，又保留诊断时看原文的能力。若 MCP 返回巨型 JSON，我会：先返回 schema/关键字段摘要；把完整载荷存 artifact；工具结果里带 `artifactId`；模型或后续工具再按字段路径拉取。截断时优先保留错误码、id、时间戳、与当前 query 相关的字段，而不是头 N 个字符一刀切。

**【项目锚点】** Citation 二次查询 · `PROTOCOL.md`  
**【解释】** 把「没做 MCP」转成「同构方案已验证」，分很高。

## A6. 模型回复过度共情，长期会情感依赖，Prompt 怎么控边界？

**【口述稿】**  
System 里明确角色：文档问答助手，**不扮演情感陪伴、不主动共情延长对话**；用户偏题（比如让写诗、谈心情）拉回「请问制度/文档相关问题」，必要时拒答。我评测里有「帮我写赞美公司的诗」这类题，期望是拒绝并说明职责边界。情感依赖更多靠产品策略和人工介入，不是单靠一句 Prompt，但 Prompt 是第一道边界。

**【项目锚点】** Q23 拒答写诗 · System 定位  
**【解释】** 阿里爱问「边界」，答角色定义 + 偏题拉回即可。

## A7. A2A 协议和 MCP 分别解决什么？什么场景用哪个？

**【口述稿】**  
**MCP** 解决的是 Agent 如何标准地连接工具和资源——像「USB」，让模型调用搜索、文件系统、数据库时有统一协议。**A2A** 解决的是 Agent 与 Agent 之间如何发现、委托、协作——像「服务间通信」。单助手 + 若干工具，用 MCP（或等价的 Function Calling）就够；多个专家 Agent 要分工（检索专家、合规专家、写作专家）且跨团队部署，再上 A2A。我当前是**进程内 Function Calling** 调 `search_docs`/`list_documents`，等价于本地工具调用；演进可以把检索封成 MCP tool，多专家场景再考虑 A2A，而不是一上来上多 Agent 网。

**【项目锚点】** `TOOL_DEFINITIONS` · 手写 tool loop  
**【解释】** 对比记忆：MCP=连工具，A2A=连 Agent。

## A8. 检索为空或超时时，Prompt 上怎么兜底？

**【口述稿】**  
空检索我做成了产品路径：首次 `search_docs` 空命中时，服务端**改写 query 再搜一次**，仍计入次数上限；`usage` 里能看到 `rewriteUsed` 和 `searchQueries`。若仍空，Prompt 要求明确拒答，不能编造。超时或上游错误走 SSE `error`，并带可重试信息。Prompt 层写死「没有工具证据就说未找到」。两端一起兜：编排兜底 + 话术兜底。

**【项目锚点】** P2 空召回改写 · `MAX_SEARCH_CALLS=2` · 拒答  
**【解释】** 别只说「Prompt 写一句未找到」，要提二次检索。

## A9. Token 消耗越来越大，怎么控制单次会话预算？

**【口述稿】**  
四刀：第一，历史窗口最多约 **8 条消息、累计约 3000 字**；第二，**不把上轮检索全文默认带进下一轮**，每轮工具结果是新的；第三，`search_docs` 全会话最多 2 次，工具 top_k 有上限；第四，推给前端的 citation 只是短 snippet。这样单次会话成本和串味都可控。若还要压，可以对更早轮次做摘要，或把大工具结果改成 artifact 指针。

**【项目锚点】** `app/agent/history.py` · `MAX_HISTORY_MESSAGES/CHARS`  
**【解释】** 预算=窗口+工具次数+结果体积，三点都要提。

## A10. 怎么判断业务该走 Workflow 还是交给 Agent 自主决策？

**【口述稿】**  
看三件事：流程是否确定性高、失败是否可逆、是否需要探索。我项目里**文档解析是 Workflow**：pending→parsing→indexing→ready，状态机 + 队列，不让模型自由发挥。**问答是有界 Agent**：可以选何时调用搜索，但工具集合小、次数有硬顶。制度问答如果完全开放 Agent，成本和乱跳工具的风险都高。经验法则：能画成流程图且步骤固定 → Workflow；需要根据中间观察分支 → Agent；也可以 Workflow 里嵌一小段 Agent。

**【项目锚点】** 文档状态机 · 有界 tool loop  
**【解释】** 用自己项目的「双模式」举例最有说服力。

---

## A11. ReAct 多步时动作空间太大容易乱跳，怎么约束工具调用顺序？

**【口述稿】**  
我用的是 Function Calling 循环，思想接近 ReAct。约束方式：工具白名单只有检索类；system 提示先检索再作答；`search_docs` 次数封顶；总轮次上限。复杂且顺序敏感的业务（比如先鉴权再支付）更适合**状态机锁死顺序**，而不是纯 ReAct。文档问答动作空间小，所以硬顶 + 提示就够，不必上大规划器。

**【项目锚点】** `MAX_TOOL_ROUNDS` · `MAX_SEARCH_CALLS`  
**【解释】** 「缩小动作空间」比「让模型更聪明」优先。

---

## A12. 怎么保证模型稳定输出 JSON 调工具？格式不对代码怎么兜底？

**【口述稿】**  
我不依赖模型在正文里手写 JSON，而是走 **OpenAI 兼容的 tools / tool_calls**，由协议层给出结构化参数。代码侧解析 `arguments`，失败就记错误或把错误作为 tool 结果回灌，**不会静默当成成功去搜**。若格式持续不稳定，可以加重试或上 constrained decoding；我当前主路径已经是原生 tool 协议，比 Prompt「请输出 JSON」稳得多。

**【项目锚点】** `chat_with_tools` · `parse_tool_args`  
**【解释】** 强调「协议 > Prompt 约束」。

## A13. Agent 多步推理时，中间步骤怎么流式回前端，而不是全部跑完？

**【口述稿】**  
这是我端上体验的核心：服务端用 **SSE** 推事件——`message.accepted` 表示接单，`tool.started` / `tool.completed` 展示检索轨迹，`message.delta` 流式出字，最后 `message.completed` 带 citations 和 usage。RN 分包按事件渲染工具卡和气泡。用户点停止会先 `POST /v1/chat/cancel` 再断开 SSE，服务端可 close 进行中的 LLM HTTP。这样用户在多步过程中一直有反馈，不用干等。

**【项目锚点】** `iter_agent_sse` · RN `streamChat` · P3-D15 cancel  
**【解释】** 阿里云高频加分题，务必结合演示讲。

## A14. 多 Agent 拆分边界？什么情况下不该拆？

**【口述稿】**  
拆的信号：权限域不同、模型规格不同、或长任务可真并行。不该拆：单域问答、共享同一事实源、拆完只是增加消息转发。我的文档 Agent **刻意保持单 Agent**，避免状态不一致和调试成本。多 Agent 辩论之类对手册事实题收益有限，还会放大幻觉协商。

**【解释】** 「不拆」讲清理由，比硬说「我用了多 Agent」加分。

---

## A15. 多个工具并发，部分成功部分失败，怎么汇总给模型？

**【口述稿】**  
每个工具结果应自带成功/失败状态和错误信息，**失败项标明不可用，禁止模型拿失败结果当证据**。我当前检索路径以串行为主，一次 search 的对错很清晰。若并发 fan-out，会在回灌 messages 里并列各 tool 的 JSON，并在 Prompt 要求「仅使用 ok 的结果」。

**【解释】** 重点是「失败可见 + 不可当证据」。

## A16. 上下文越来越长，有哪些压缩方法，尽量不丢信息？

**【口述稿】**  
我已做的：历史截断、工具结果截断、citation 短 snippet + 二次拉全文。还可做：对更早对话摘要、只保留 chunkId 列表、分层记忆（热缓存当前轮，冷存会话库）。原则是**把大内容外置，上下文只留可检索的钥匙**。

## A17. 阿里云一面补充：MinerU / Milvus / Cross-encoder / Guardrail（若被问到）

### A17-1 表、公式、图进向量库？索引策略是否一样？

**【口述稿】**  
我用的是 PyMuPDF + OCR，不是 MinerU；正文唯一来源在 **SQLite**，FAISS 只存向量和 chunkId，**没有上 Milvus**。图目前没有单独建多模态索引，扫描页走 OCR 转成文本再进同一套 chunk。若表/公式/图都要检，常见做法是：文本一套稠密索引；图用 caption 或多模态 embedding，对象存 OSS，元数据统一挂 documentId。索引策略可以不同，但 **id 体系要统一**，方便引用。

### A17-2 Cross-encoder 大概延迟？文档量很大怎么办？

**【口述稿】**  
我用的是云端 rerank API，先 FAISS 拉候选再精排，用候选数量控延迟，没有本地 CE 的压测数字，所以我不报具体毫秒。大批量文档靠**按 KB 隔离 + 增量 FAISS**，避免每次全库 CE。原则是：永远不要对全库跑 cross-encoder。

### A17-3 Guardrail 词典还是分类模型？敏感词后路径？危机几级？

**【口述稿】**  
我目前是薄鉴权 + Prompt 拒答，没有完整安全中台。生产上通常规则词典做快拦，分类模型做语义风险；命中后路径是拦截 / 改写 / 转人工。危机分级一般从自动拒答、降级话术到强制人工。我没产品化 HITL，但知道高敏工具必须 Human-in-the-loop。

### A17-4 何时 API、何时本地部署？

**【口述稿】**  
我演示链路全走通义 API，迭代快、运维简单。选本地通常因为数据不出域、要控尾延迟或成本打满。模型选择看：任务是生成还是 Embedding/Rerank、中文制度语料效果、单价与限流。

### A17-5 垂域 Embedding 语义偏移，除了混合检索和 Rerank 还有？

**【口述稿】**  
我还做了 query 改写和指代改写、结构化切分保条款。另外还可以：垂域微调、同义词表、硬负例、HyDE（慎用）。我没做 LoRA，优先改检索管线因为性价比高。

# 第三部分 · 蚂蚁 AI 应用开发二面（按面经原题）

## B1. 用 MinerU 解析时，跨多页的表格如何保证语义完整？

**【口述稿】**  
先对齐技术栈：我**没有用 MinerU**，解析是 PyMuPDF，扫描件走通义 OCR，docx 用 python-docx 抽表。跨页表在我这套里**可能被页边界切断**，这是已知限制。若用 MinerU 或自研，我会：检测跨页续表并合并；用表标题/表头作为锚；合并后再切分，或父 chunk 存整表摘要、子 chunk 存行。面试里我不会假装已经完美解决跨页表，但方案路径是清楚的。

**【项目锚点】** `extract.py` / OCR · `KNOWN_ISSUES`  
**【解释】** 蚂蚁爱问 MinerU——诚实 + 方案 > 硬蹭。

---

## B2. 讲一下 Ragas 评测。

**【口述稿】**  
Ragas 是 RAG 自动评测框架，常见指标包括：**Faithfulness**（答案是否忠于上下文）、**Answer Relevance**（是否答所问）、**Context Precision/Recall**（检索上下文是否准、是否全）等，多用 LLM-as-judge。我项目**没有直接接入 Ragas**，而是自建评测：固定 ACME 手册 + 25 题，对 `expectMust`/`expectAny`/拒答/`forbidden` 做粗判，失败写入 `FAILURE_CASES` 人工归因，点踩可导出候选。思想对齐——都要拆「检索质量 vs 生成质量」——实现更轻，适合个人项目快速回归。最近一次 25/25 粗判通过，但我强调粗判会误杀，不能当金标准。

**【项目锚点】** `scripts/run_eval.py` · `eval/FAILURE_CASES.md` · P3-D8 反馈  
**【解释】** 会讲指标含义，再 bridging 到自己的评测，最加分。

---

## B3. Answer Relevance 分数偏低，怎么判断是检索差还是模型能力差？

**【口述稿】**  
拆开看上下文：如果检索 hits 里根本没有金句，citations 也对不上，那是**检索/切分**问题；如果 hits 里已有正确答案片段，但模型答非所问或瞎总结，那是**生成/Prompt**问题。我排障时看 `requestId` 对齐的 `toolTrace`、`searchQueries`、是否触发改写、以及答案里的 `[n]` 是否合法。FAILURE_CASES 里也会标归因类型。没有上线 Ragas AR 分数，但排查逻辑一样。

**【项目锚点】** usage / toolTrace / FAILURE 归因模板  
**【解释】** 这题考「因果拆解」，用你的可观测字段答。

---

## B4. LangGraph 里 State 如何定义和传递？

**【口述稿】**  
我实现的是**手写 Tool Loop，不是 LangGraph**。等价的「State」主要是：messages 列表（system/user/assistant/tool）、本轮 hits、usage 计数、cancel 标记；会话落在 SQLite。每一轮模型若返回 tool_calls，执行后以 role=tool 写回 messages，再调模型。如果用 LangGraph，通常会用 Typed state，节点读写字段，靠边传递。我选择手写是为了把 SSE 事件、次数上限、取消绑死在自己的控制流里，调试更直观。

**【项目锚点】** `agent_stream.py` · messages 回灌  
**【解释】** 不要说「我用了 LangGraph」；说「State 在我这是什么」。

---

## B5. 任务节点很多时，如何避免 State 过大导致内存溢出？

**【口述稿】**  
原则是 State 里只留**摘要和引用，不留大对象全文**。我已经：历史消息截断到 8 条/3000 字；工具 hit 截断；不把上轮全文检索默认带入。生产图编排还会：checkpoint 外置、中间结果写 DB/文件、state 只存 id。节点再多，也不能让每层都 append 原始大 JSON。

**【项目锚点】** `history.py` · citation snippet  
**【解释】** 和阿里「Token 预算」同一套答案，蚂蚁用 State/OOM 包装。

---

## B6. 长期记忆如何把多轮对话蒸馏成结构化用户画像并写入向量库？

**【口述稿】**  
我**刻意没有做跨会话用户画像向量库**。原因：制度问答要防串味和隐私，每轮检索应回到文档，而不是「用户说过什么」。当前只有会话内短窗口。若做长期记忆，会定期用模型把多轮蒸馏成结构化 profile（偏好、角色、未决问题），写入 KV 或向量库，读取时与文档检索隔离，并允许用户清除。那是陪伴/个人助手场景的设计，不是我这个产品的主路径。

**【解释】** 「不做」讲清产品原因，显得有判断。

---

## B7. 文档切分时 overlap 的作用是什么？

**【口述稿】**  
overlap 让相邻 chunk 共享边界上下文，降低「一句话正好从中间切断、两边都检索不完整」的概率。但 overlap 太大会重复、噪声和成本上升。我优先**按标题和段落切**，再在过长段落上开窗口，比纯固定窗+盲目加大 overlap 更保条款完整。

**【项目锚点】** P3-D3  
**【解释】** 先讲目的，再讲与结构切分的关系。

---

## B8. chunk size 和上下文完整性怎么权衡？

**【口述稿】**  
chunk 太小：引用碎、条款不完整；太大：检索噪声高、塞进 Prompt 贵且干扰。我的权衡是结构优先——尽量在标题/段落边界切——再用长度封顶。最终靠**固定题评测**看条款问答是否还完整，而不是拍脑袋定 500 字。

**【解释】** 「评测驱动切分」是亮点句。

---

## B9. 了解 GraphRAG 吗？请介绍一下。

**【口述稿】**  
GraphRAG 在文本外再构**实体-关系图**，查询时结合社区摘要或图遍历，适合人物、组织、多跳关系类问题。我的员工手册场景以条款事实为主，用向量检索 + 结构化切分 + Rerank 性价比更高，**没有上 GraphRAG**。若问题变成「谁向谁汇报、系统依赖哪些服务」，再考虑抽图。生成阶段若图召回很噪，要用 Rerank 或 Self-Reflection 按证据过滤，不能全塞给模型。

**【解释】** 定义 → 适用 → 我为何不用 → 噪声怎么滤。

---

## B10. GraphRAG 召回很多相关信息时，生成阶段如何用 Self-Reflection 或 CoT 过滤噪声？

**【口述稿】**  
生成前先截断（我用 Rerank 控候选）；生成时 Prompt 要求逐条有据、无据不写；还可以第二轮 Reflection：「检查每个论断是否能在给定上下文找到支撑，删掉无依据句子」。我线上没有单独 Reflection 节点，但用了**引用收紧**：模型不写 `[n]` 就不挂假 citation，逼回答可溯源。这和 Reflection「无证据删除」是同一目标的轻量实现。

**【项目锚点】** P3-D2 引用策略 · Rerank  
**【解释】** 把未做的 Reflection 映射到已做的引用策略。

---

# 第四部分 · 蚂蚁/阿里后半场共性深化题（面经图里后半页）

> 以下题在多场「AI 应用」面经反复出现；口述稿按 docs-agent 写，两边可背同一套。

---

## C1. Agent 长程任务中间步骤一堆结果，怎么结构化存储，防止上下文被低价值信息污染？

**【口述稿】**  
中间结果进工作区或数据库，上下文只保留**摘要 + id**。我这边工具命中不长期污染下一轮；citation 只留 snippet。长任务应写「步骤日志表」，模型每步只看当前目标和下一步所需字段。

---

## C2. Agentic RAG 里 Agent 怎么判断检索够不够？什么时候停止检索直接回答？

**【口述稿】**  
有足够可引用证据就进入最终回答；空则改写再搜；达到 `search_docs` 上限仍不够就拒答或如实说不足。我没有单独的 sufficiency 模型，用**硬顶 + 是否空命中**做决策，可观测、成本可控。

**【项目锚点】** `MAX_SEARCH_CALLS=2` · 空召回改写  

---

## C3. 多 Agent 辩论如何提升答案质量？辩偏了怎么拉回？

**【口述稿】**  
正反方独立给结论，裁判按证据裁决，能减少单模型自信幻觉。但辩偏时必须用**原问题 + 检索证据**作硬约束，超时强制收敛。手册事实题我倾向单 Agent + 引用，辩论性价比不高。

---

## C4. Agent 怎么从历史成功/失败案例学习？经验库存什么？后续怎么复用？

**【口述稿】**  
我存的是评测失败归因和用户点踩导出：问题、答案、requestId、归因类型。复用方式目前是人工改切分/Prompt/题库。进阶是相似题检索，把正确答法当 few-shot 注入。我还没做自动注入，但数据闭环已经打通到 `feedback_candidates.jsonl`。

**【项目锚点】** P3-D8 · `FAILURE_CASES.md`  

---

## C5. Skills 和普通 Tool 调用的区别？按需加载一般怎么实现？

**【口述稿】**  
Tool 是单次函数；Skill 是「说明文档 + 一组工具 + 推荐流程」的能力包，按意图加载，避免把全部工具 schema 塞进上下文。我目前是启动时固定注册少量工具。按需加载可以用意图分类或检索 Skill 目录后再动态加入 tools 参数。

---

## C6. Agent 多步规划时中间结果不符预期，怎么动态调整而不是死抱初案？

**【口述稿】**  
空检索触发改写再搜就是一种局部重规划；仍失败则停止并拒答，而不是无限换 query。更大系统会设 re-plan 节点，把失败写入 state 再分支。关键是**允许失败退出**，防止死循环烧 Token。

---

## C7. 推理时 Scaling 在 Agent 场景怎么体现？

**【口述稿】**  
同一问题允许多次检索、改写、自洽投票，用更多测试时算力换质量。但我必须加**预算硬顶**，否则成本不可控。我的 Scaling 是有界的：最多两轮 search、有限 tool 轮次。

---

## C8. HyDE 用假设答案做检索，什么场景好用、什么场景引入噪声？

**【口述稿】**  
用户问法短、和文档措辞鸿沟大时，假设答案可能更好召回。精确数字、拒答、或假设答写错时，会把检索带偏。我用的是**基于真实问题的改写**，不是 HyDE。

---

## C9. 了解 Late Chunking 吗？和先分块再 Embedding 有何区别？

**【口述稿】**  
传统是先切 chunk 再分别 embedding。Late Chunking 倾向先对长文（或大段）编码，再得到各块表示，跨块上下文保留更好，但算力更贵。我是经典先切再 embed，配合结构切分。

---

## C10. Constrained Decoding 和 Prompt 约束 JSON，实际选哪个？局限？

**【口述稿】**  
调工具我选**官方 tool 协议**，比纯 Prompt 约束 JSON 稳。Constrained Decoding 在必须严格 schema 时可上，但依赖推理栈，移植性差一点。Prompt 约束便宜但不稳，只适合演示。

---

## C11. 提示词注入怎么防？用户说「请忽略之前的指令」怎么处理？

**【口述稿】**  
系统指令与用户输入隔离；工具返回当数据不当指令；回答只允许基于文档证据。对「忽略之前指令」，视为普通用户文本，**不提升权限、不关闭拒答策略**。高危操作需要鉴权与确认。Key 只在服务端。我有 Bearer Token，但没有专用注入分类器，边界靠架构而不是靠「再写一句你不能忽略」。

---

## C12. 讲一下 ReAct 原理，为什么能提升复杂任务理解？

**【口述稿】**  
ReAct 让模型交错输出推理与行动：想一步、调工具、观察结果、再想。复杂任务被拆成可验证的小步，能根据观察纠错，而不是一次空想到底。我的 FC 循环就是这套：tool_calls → 执行 → 回灌 → 再决策，并加了次数上限防失控。

---

## C13. 工具参数幻觉或语法错误，有哪些自动修正手段？

**【口述稿】**  
Schema 校验失败则重试或返回错误让模型改；必要时用修复提示；仍失败则拒绝执行。我解析 args 失败不会假装成功。参数幻觉还要靠缩小工具参数空间和给清晰 description。

---

## C14. Multi-Agent 中心化编排 vs 点对点？

**【口述稿】**  
中心化有主编排器，易审计、易限流、易统一取消；点对点灵活但难排查。我单 Agent 中心环路，等价于最简中心化。

---

## C15. Agent 的 Self-Reflection 如何识别输出逻辑错误？

**【口述稿】**  
二次审视：是否自相矛盾、是否每句有上下文支撑、是否答非所问。实现上可以第二模型或同一模型换「审查者」角色。我用引用合法性 + 离线评测做弱 Reflection；在线全自动审查还没上。

---

## C16. 如何设计 Agent 长期记忆？

**【口述稿】**  
分情景记忆（对话摘要）、语义记忆（事实/画像）、程序记忆（成功技能）。写入要过滤，读取要与当前任务相关，并支持遗忘。我只做会话短记忆 + 文档检索当「世界知识」。

---

## C17. 支付等高敏操作如何 Human-in-the-loop？

**【口述稿】**  
工具分只读与高危；高危只生成「待确认计划」，人工批准前不执行；全程审计。我文档删除/reparse 在演示里较直接，生产应加确认态——思想同源。

---

## C18. 如何设计一个 Skill？Skill 和 MCP 对比？

**【口述稿】**  
Skill：名称、适用场景、说明书、工具列表、可选工作流。MCP：跨运行时暴露工具/资源的协议。Skill 偏产品与提示组织；MCP 偏互通标准。可以「一个 Skill 背后挂一组 MCP tools」。

---

## C19. 什么是上下文缓存？对冗余系统指令有何优势？

**【口述稿】**  
把反复出现的长前缀（system、工具定义）缓存在推理服务侧，复用时降延迟和成本。Agent 每轮都带长工具列表时收益明显。我了解这一能力，演示环境未单独对接厂商 cache 配置。

---

## C20. 自然语言任务如何变成可靠执行路径？

**【口述稿】**  
自然语言 → 有界计划 → 校验（schema/权限）→ 执行 → 观察 → 必要时重规划。可靠性来自约束与校验，不是来自更长 Prompt。我用有界工具 + 状态机解析体现这一点。

---

## C21. Vibe Coding 怎么理解？有什么经验？

**【口述稿】**  
用 AI 快速出原型可以，但必须用工程护栏收口：契约、评测、错误码、可观测。我的项目就是边生成边用 25 题回归和 FAILURE 归因，避免「能跑但不可信」。

---

## C22. OpenClaw 如何增强本地文件/代码执行感知？（若不熟）

**【口述稿】**  
我没有用过 OpenClaw 这个具体项目。若指本地 Agent 操作文件与代码沙箱，关键是**最小权限、路径白名单、审计日志、与云端 Key 隔离**。我的架构是文件上传到服务端再解析，端上不直接拿大模型去扫本地盘。

**【解释】** 不熟就别编；讲权限模型即可。

# 第五部分 · 阿里云 vs 蚂蚁：同题对照（背诵时选侧重点）

| 主题 | 阿里云更想听 | 蚂蚁更想听 | 你共用的项目事实 |
|------|--------------|------------|------------------|
| 解析 | 跨元素关系、数字敏感 | MinerU 跨页表 | 结构切分 + OCR；承认跨页/跨元素未做完 |
| 评测 | 粗判/回归即可 | Ragas 指标与 AR 拆因 | 25 题 + FAILURE + toolTrace 拆检索/生成 |
| 编排 | Workflow vs Agent、SSE | LangGraph State / OOM | 解析状态机 + 手写 loop + 历史截断 |
| 检索增强 | Rerank 延迟、垂域偏移 | GraphRAG / HyDE / Late Chunking | Rerank + 改写；图/HyDE/Late 口述边界 |
| 工具生态 | MCP 大 JSON、A2A | Skill / MCP 对比 | snippet + 二次拉取；进程内 FC |
| 安全 | 共情边界、注入 | HITL、危机分级 | Prompt 边界 + Bearer；HITL 口述 |

**两边共用金句（建议背）：**  
1. 「解析走 Workflow，问答走有界 Agent。」  
2. 「向量库只存向量，正文以 SQLite 为单一事实来源。」  
3. 「空检索改写再搜，次数封顶，仍空就拒答。」  
4. 「SSE 先 tool 再 delta；停止能 cancel 打断 HTTP。」  
5. 「没做的能力我讲清适用边界和下一步，不硬蹭名词。」
